```typescript
const handlePlayerSelect = (playerId: string) => {
  if (!playerId) {
    setForm((f) => ({ ...f, playerId: '' }));
    return;
  }
  const player = players.find((p) => p.id === playerId);
  if (player) {
    setForm((f) => ({
      ...f,
      playerId,
      playerName: `${player.firstName} ${player.lastName}`,
      position: player.position,
    }));
  }
};
```

## Trust Boundaries

| User input → Dexie `players.update` | createDraftPick writes a hard-coded `status: 'drafted'` to a player row when `pick.playerId` is set. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-24-04-01 | Tampering | createDraftPick player-status side effect | mitigate | Status value is a hard-coded literal `'drafted'`, not user-supplied; no path for an attacker to write an arbitrary status string through this code. `db.players.update` accepts `Partial<Player>`, narrowing the writable surface. |
| T-24-04-02 | Information Disclosure | Combobox search | accept | The combobox filters over the in-memory `players` array already loaded for this page; the search does not query Dexie or expose any data the user cannot already see. |
| T-24-04-03 | Repudiation | Status side effect is silent | accept | Per D-12 the side effect is intentionally silent; coaches see the status change next time they navigate to RosterPage. `updatedAt` is stamped on every write so the change is auditable in DB. |
| T-24-04-04 | Denial of Service | Dexie no-op on missing playerId | accept | Per Pitfall #5, `db.players.update(missingId, ...)` silently returns 0 affected rows. The downstream draft pick insert is unaffected; no exception propagates. |
</threat_model>
