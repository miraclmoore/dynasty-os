```rust
use tauri_plugin_store::StoreExt;
use serde_json::Value;

#[tauri::command]
async fn call_anthropic(
    app: tauri::AppHandle,
    body: Value,
) -> Result<Value, String> {
    // Read API key from plugin-store (never from frontend) per D-05
    let store = app.store("dynasty-os.bin").map_err(|e| e.to_string())?;
    let api_key = store
        .get("anthropic-api-key")
        .and_then(|v| v.as_str().map(|s| s.to_string()))
        .ok_or_else(|| "No API key configured".to_string())?;

    let client = reqwest::Client::new();
    let response = client
        .post("https://api.anthropic.com/v1/messages")
        .header("x-api-key", &api_key)
        .header("anthropic-version", "2023-06-01")
        .header("content-type", "application/json")
        .json(&body)
        .send()
        .await
        .map_err(|e| e.to_string())?;

    let json: Value = response.json().await.map_err(|e| e.to_string())?;
    Ok(json)
}

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .plugin(tauri_plugin_store::Builder::default().build())
        .plugin(tauri_plugin_dialog::init())
        .plugin(tauri_plugin_fs::init())
        .plugin(tauri_plugin_shell::init())
        .invoke_handler(tauri::generate_handler![call_anthropic])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WebView -> Rust | Untrusted JSON `body` payload crosses from frontend (`invoke`) into Rust `call_anthropic`. The Rust side controls headers and key injection. |
| Rust -> Anthropic API | Outbound HTTPS request from Rust process. Bypasses WebView entirely (the security goal). |
| Plugin-store file `dynasty-os.bin` | OS-native encrypted store on disk. Only the Tauri runtime (with the app's identifier) can read it. |
| localStorage (WebView) | Will hold the legacy API key only until first launch post-Phase-20, then deleted by `migrateApiKey`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20-01 | Information Disclosure | Anthropic API key in `localStorage` (DevTools-readable) | mitigate | Move key to `dynasty-os.bin` plugin-store; Rust reads key directly via `app.store("dynasty-os.bin").get("anthropic-api-key")`. Key never returned to frontend (only `hasApiKey: boolean` exposed via PrefsStore per D-05/D-07). |
| T-20-02 | Information Disclosure | API key visible in WebView memory / fetch network panel | mitigate | All Anthropic calls move to Rust via `call_anthropic`. Frontend never holds the key string after migration. `ai-bridge.ts` accepts only `{ model, max_tokens, system, messages }` — never headers or auth. |
| T-20-03 | Tampering | Frontend could craft an arbitrary `body` and exfiltrate the key by injecting an Anthropic prompt that echoes secrets | accept | The key never appears in the prompt body — Rust injects it as an HTTP header only. Anthropic responses contain model output, never headers. Worst case: an attacker who already has WebView code execution could spam the API (cost) but cannot exfiltrate the key. Acceptable because gaining WebView code execution implies the device is already compromised. |
| T-20-04 | Tampering | `body` Value passthrough lets frontend send arbitrary fields to Anthropic | accept | The Anthropic endpoint validates its own request schema. We do not whitelist fields because doing so would lock us into a specific schema version and break when Anthropic adds capabilities. Per D-03, the passthrough is intentional. |
| T-20-05 | Denial of Service | Malicious or buggy frontend could spam `call_anthropic` and exhaust Anthropic quota / billing | accept | No rate limiting in V1. Single-user desktop app — same threat existed pre-Phase-20 with direct fetch. Future enhancement: rate-limit in Rust if abuse observed. |
| T-20-06 | Repudiation | No audit log of which app code path triggered each Anthropic call | accept | Single-user, local-only app. No multi-actor scenario; no compliance requirement. |
| T-20-07 | Information Disclosure | `dynasty-os.bin` on disk could be read by other processes on the same OS user account | accept | Standard OS-level file permissions apply. `tauri-plugin-store` v2 stores in app-data directory with default perms. Encrypting at rest is out of scope for V1 (would require user-managed unlock UX). Documented limitation. |
| T-20-08 | Spoofing | A different desktop app on the same machine could call `app.store("dynasty-os.bin")` if it knew the path | accept | App-data directory is namespaced by `tauri.conf.json` identifier. Cross-app reads require deliberate path traversal which the OS sandbox prevents for properly-installed apps. |
